# 図解とGoogleドキュメント納品の作り方

(ファイル名は導入時の名残。今の中身は「図解の作り方」と「Googleドキュメントへの入れ方」)

**2026年9月以降、WordPress貼り付け用のHTMLは作らない。** まえちゃんから明示的に
不要と言われたため。納品の主役は **Googleドキュメント（本文＋図の挿入位置）＋
図解のPNG画像ファイル。** 画像はドキュメントに自動で埋め込まず、まえちゃんが
自分でドラッグ&ドロップして貼る前提で渡す(理由は SKILL.md の該当セクション参照)。

```bash
S=.claude/skills/homepage-article/scripts

```

## Markdownに書く指示コメント

本文のMarkdownに直接書く。これで図・写真・ボックスの位置が決まる。
**wp.html生成はしなくなったが、このコメント記法は記事の構成メモとして今後も使う**
（どの段落がボックスで、どこに図が要るかを自分で見失わないため）。

| 書き方 | 効果 |
|---|---|
| `<!-- fig: キー -->` | figures.py の該当図。Googleドキュメントではこの位置に「［図N：キャプション］」という1行プレースホルダーとして書く |
| `<!-- photo: 説明 \| alt \| ファイル名 -->` | 写真が要る位置のメモ（まえちゃんに別途撮影を頼む） |
| `<!-- box: crit\|warn\|good\|info \| ラベル -->` | 直後の段落が「注意ボックス」相当の内容だという構成メモ |
| `<!-- sns: 導入文 -->` | 中盤のYouTube導線を入れる位置 |
| `**テキスト**` | 強調したい語句 |

### ボックス相当の内容の使い分け(色は使わないが、構成としては維持する)

| 種類 | 使いどころ |
|---|---|
| `crit` | 「こう答える会社は要注意」— 危ないサイン |
| `warn` | 年度で変わる制度の但し書き、注意事項 |
| `good` | やるべきこと、良い状態の説明 |
| `info` | 「この記事で分かること」などの案内 |

**1記事につき crit 相当の強い注意喚起は2〜3個まで。** 増やすと効かなくなる。

## 図解は「SVGで作る」か「画像生成プロンプトを渡す」かを最初に決める

2026年9月、まえちゃんの指示により、**図解の一部をGPT（ChatGPT等の画像生成）に置き換える運用**
になった。ただし画像生成は数字・文字の正確な描画が苦手なので、**内容によって作り方を分ける。**

| 図の性質 | 作り方 |
|---|---|
| **数値が主役**（比較グラフ、基準表、スケール図、坪単価・C値などの実数を見せる図） | **これまで通りSVGで作る**（下の「図解の書き方」）。数字を画像生成に任せると誤った値が載るリスクがあるため |
| **概念・関係性を示す図**（AとBの違いの模式図、体制の図、仕組みを示す図で、文字ラベルが最小限でよいもの） | **画像生成プロンプトを作ってまえちゃんに渡す**（下の「画像生成プロンプトの作り方」）。SendUserFileでPNGを送るのではなく、プロンプト文字列をチャットに書いて渡す |

迷ったら数値が1つでも本質的に関わる図はSVG側に倒す。**画像生成の図にラベルや数値を
入れようとしない**（崩れる前提で設計しない）。

## 画像生成プロンプトの作り方（概念図・イラスト・写真共通）

ChatGPT等の画像生成にそのまま貼れるプロンプトを日本語で書く。**プロンプトを作って渡すのが
成果物であり、画像そのものは生成しない**（まえちゃんがGPTに投げて生成する運用）。

毎回、次のスタイル文をプロンプトの先頭に付ける（記事ごとに変えない。サイト全体の絵柄を揃えるため）。

```
スタイル：シンプルでフラットなインフォグラフィック風イラスト。線画+淡い色面。文字・数字・ラベルは一切入れない（文字はこちらで別途重ねるか、キャプションで説明する）。アースカラー（ベージュ・淡いグリーン・グリーン系）を基調にした配色。装飾的すぎず、建築・住宅系の落ち着いた雰囲気。16:9の横長構図。背景は無地かごくシンプル。
```

**実際の施工写真の代わりに使う人物・現場写真**（`<!-- photo: ... -->`の位置）は、上のフラット
イラストと役割が違うので、別のスタイル文を使う。

```
スタイル：フォトリアルな建築写真風。自然光、暖色系のナチュラルな色調。日本の現代住宅・工務店のオフィスの雰囲気。画像内に文字・ロゴ・看板の文字は入れない。人物の顔は正面からはっきり写さない（後ろ姿・横顔・手元のクローズアップなどで表現）。16:9の横長構図。
```

### 守ること

- **文字・数字・ラベルは入れない指示を必ず書く。** 画像生成で文字を入れようとすると高確率で
  崩れる。ラベルが要る内容は、そもそもSVG側に回す
- **「施工事例」と誤解される書き方をしない。** AI生成画像は実際の自社施工写真ではないので、
  altテキストやキャプションで「イメージ画像」と分かるようにすることをまえちゃんに伝える
  （プロンプト自体にはここまで書かなくてよいが、納品メッセージで一言添える）
- プロンプトは**具体的に**（画角、構図、光の当たり方、何を主役にするか）。抽象的な指示だけだと
  絵柄がブレる
- 記事1本につき、この対象になる図が複数あれば**まとめてプロンプトを列挙する**（1つずつ確認を
  待たない）

## 図解の書き方（数値が主役の図。SVGで作る場合）

`articles/<slug>.figures.py` に、次の形で書く。

```python
from svg_kit import *          # 共通部品と検証済みパレット

def fig_example():
    W, H = 880, 400            # 幅は必ず 880（STD_W）
    s = []
    s.append(txt(0, 28, '図の言いたいこと', 17, INK, '700'))
    s.append(box(0, 50, 420, 300, TINT, LINE))
    ...
    return wrap(''.join(s), W, H,
                'スクリーンリーダー用のタイトル',
                '図の内容を文章で説明したもの')

FIGURES = {'example': (fig_example, '図1：キャプション')}
```

### 守ること

- **幅は880固定で描く。** PNG書き出し時にドキュメント用の表示幅(480〜620px程度)へ
  縮小する。元を880で描いておけば、縮小しても文字がにじまない
- **色は `svg_kit` の定数だけを使う。** 新しい色を足さない
  （dataviz スキルの検証済みパレットに揃えてある）
- **`wrap()` の title / desc を必ず書く。** 図の内容を文章で言い切れるかの確認にもなる
- **色だけで意味を伝えない。** ✓／✕／ラベルを必ず添える
- **SVGで自作のイラストは描かない。**(2026年9月、house_icon()等を試作したがまえちゃんの
  イメージと合わず不採用) SVGはテキスト・図形（四角・円・矢印）・数値の可視化に徹する。
  イラスト・装飾的な絵が欲しい場合は、SVGで描こうとせず上の「画像生成プロンプトの作り方」に回す
- **文字サイズは「分かりやすさ」を最優先する。** 880幅の描画時点で、見出し18〜20px、
  本文ラベル（カードの中の言葉など）15px以上、注記・補足でも14px以上を下限にする。
  過去に11〜12pxの注記を書いたことがあるが、縮小後に読みにくくなるので今後はやらない。
  「これ以上小さくしたら読めるか」を都度、実際に書き出したPNGで確認すること
- **文字の強弱でも分かりやすさを作る。** 一番伝えたい語句・数字は`weight='700'`で
  太くする、それ以外は`INK2`（やや薄いグレー）で色の強弱もつける、といった
  メリハリを意識する。全部同じ太さ・同じ濃さの文字を並べない

### 図解が向くテーマ

- **2つのものの比較**（壁量計算と許容応力度計算、瑕疵保険と完成保証、一式と内訳明細）
- **段階・順序**（断熱等級、家づくりのスケジュール）
- **体制・流れ**（設計と施工の分業／一貫）

数字が主役でない限り、棒グラフや円グラフにしない。住宅記事で本当に必要なのは
**「どっちがどう違うのか」を1画面で見せる比較図**。

### 図解の内容を疑うこと

図は本文より強く記憶される。だから **本文が正確でも図が言いすぎていたら図の負け。**
たとえば「壁量計算では基礎を検討しない」は誤り（仕様の基準はある）。
正しくは「1棟ごとの個別計算はしない」。**断定する前に必ず裏を取る。**

## PNG書き出しの解像度

`export_png.py` は既定でSVGのviewBoxをそのまま2倍解像度（幅1760px前後）で書き出す。
これはWordPress時代にSVGが除去される環境向けのフォールバックとして作った経緯があり、
**Googleドキュメントに貼る用途には解像度が高すぎてファイルが重い。** ドキュメントへの
貼り付け用に渡すときは、480〜620px幅程度に縮小したものを別途書き出して渡す
（縮小方法は `export_png.py` の実装を参照。target幅を変えて呼び出す）。

## Googleドキュメントへの入れ方

1. 記事本文をMarkdownで書く（フロントマターにSEO納品セット、本文に指示コメント）
2. 指示コメントを取り除いた「読める本文」を作る。**`<!-- fig: キー -->` の位置には、
   何を貼ればいいか一目で分かるプレースホルダー行を残す。**

   ```
   ［図1：住宅完成保証と瑕疵担保責任保険が対象とする期間の違い］
   ```

3. 著者プロフィールボックス・SNS・関連記事を末尾に追加する（テンプレートは
   `seo-checklist.md` の該当セクション）
4. `mcp__Google_Drive__create_file` で `contentMimeType: text/markdown` として作成する
   （**画像は埋め込まない。理由はSKILL.mdの「なぜGoogleドキュメントに画像を自動で
   埋め込まないのか」を参照**）
5. 図解PNG（480〜620px幅に縮小したもの）を `SendUserFile` でまえちゃんに送る。
   キャプションに「どのプレースホルダーに対応するか」を明記する
   （例:「図1：住宅完成保証〜の図です。同名のプレースホルダーの位置に貼ってください」）

**一度作ったドキュメントは作り直さない。** プレースホルダーの入れ忘れに気づいても、
後から本文だけを差し替える手段が無いので、作成前に指示コメントの位置を見直しておく。
